# Архитектура

```
 Браузер ──HTTPS:443──► proxy (nginx)
                          ├── /        → статика фронтенда (Vue, собранная в файлы)
                          └── /api/*   → app (FastAPI) ──┬──► postgres (PostgreSQL 16 + pgvector)
                                                          └──► ollama (LLM + эмбеддинги, GPU)
                          worker (тот же код, другая команда) ──► postgres, ollama
 HTTP:80 → только редирект на HTTPS
```

| Контейнер | Что делает | Почему так |
|-----------|-----------|-----------|
| `proxy` | TLS, отдаёт фронтенд, проксирует `/api` | Единственная точка входа. Сертификат — из `certs/`. Для SSE отключена буферизация, иначе heartbeat застрянет в nginx. |
| `migrate` | `alembic upgrade head` и выход | app и worker стартуют только после успешной миграции — нет гонки «код новее схемы». |
| `app` | HTTP API | Лёгкие запросы пользователей; тяжёлое уходит в очередь. |
| `worker` | Фоновые задачи: синхронизация, парсинг, векторизация, граф, противоречия | Отдельный процесс: OCR скана на 200 страниц не тормозит ответы пользователям. |
| `postgres` | Все данные: документы, чанки и векторы, пользователи, граф, аудит, очередь задач | Одна БД = одна резервная копия, транзакции между векторами и правами. |
| `ollama` | qwen2.5:7b (LLM), bge-m3 (эмбеддинги) | `OLLAMA_NUM_PARALLEL=1`: в 8 ГБ VRAM два контекста 7B не помещаются. |

## Ключевые решения этапа 0

### Очередь задач в PostgreSQL
Таблица `jobs`, worker забирает задачу запросом `SELECT … FOR UPDATE SKIP LOCKED` (`backend/app/worker/queue.py`). Два worker'а не возьмут одну задачу, а задача, «зависшая» в статусе `running` после падения контейнера, возвращается в очередь при старте (`requeue_stale`). Так первичная индексация на много часов переживает перезагрузку сервера.

### Пользователи важнее фоновых задач
`backend/app/core/llm_priority.py`. Пока пользователь ждёт ответ, app держит *разделяемую* advisory-блокировку PostgreSQL. Worker перед каждым вызовом LLM пробует на мгновение взять *исключительную*: не получилось — значит, кто-то ждёт, и worker откладывает вызов. Блокировка привязана к соединению, поэтому при падении app она снимается сама. Пример: worker строит граф по 3000 чанкам, пользователь задал вопрос — следующий чанк worker не отправит в Ollama, пока ответ не закончится. Ограничение: уже отправленный worker'ом запрос (до ~20 с) пользователь дождётся, поэтому фоновые вызовы делаем по одному чанку.

### Потоковые ответы с heartbeat
`backend/app/core/sse.py`. Пока LLM молчит, каждые 2 с уходит SSE-комментарий `: ping`. Проверка вживую: `curl -k -N https://localhost/api/diag/sse?seconds=20`.

### Драйвер БД — asyncpg
psycopg 3 под LGPL-3.0, а у нас разрешены только Apache/MIT/BSD. asyncpg — Apache-2.0 и быстрее.

### Бюджет видеопамяти (GTX 1070, 8 ГБ) — оценка до замера

| Что | ≈ VRAM |
|-----|--------|
| qwen2.5:7b-instruct Q4_K_M, веса | 4,7 ГБ |
| KV-кэш при `num_ctx=8192` (28 слоёв × 4 KV-головы × 128 × 2 × fp16) | 0,5 ГБ |
| bge-m3 (fp16) | 1,2 ГБ |
| CUDA-контекст, буферы | 0,5–0,8 ГБ |
| **Итого** | **≈ 7,0 ГБ** |

Запаса ~1 ГБ, поэтому реранкер по умолчанию на CPU (open-questions #11), а `num_ctx` выше 8192 — только если замер покажет запас. Замер на сервере: `python scripts/bench/ollama_bench.py` (выводит tokens/s, время до первого токена и сколько модели реально легло на GPU).

## Фронтенд (решение на этап 1)
**shadcn-vue** (на Reka UI) + Tailwind + TanStack Table, а не PrimeVue. Причины:
- компоненты копируются в наш репозиторий как обычные `.vue`-файлы — строгий промышленный стиль задаём своими токенами, а не переопределяем чужую тему;
- оформление целиком на Tailwind и CSS-переменных — те же токены, что в дизайн-системе (`design/`);
- офлайн без сюрпризов: нет тем, подгружаемых отдельно, всё в бандле;
- для таблиц админки (тысячи документов, сортировка, фильтры) берём TanStack Table — это то, чего не хватает shadcn-vue по сравнению с PrimeVue DataTable.

Минус: компонентов «из коробки» меньше, чем у PrimeVue (нет готового дерева, календаря диапазона и т. п.), — дописываем по мере надобности.

## Этап 1: вход, сессии, роли и права

### Вход
```
Браузер ──POST /api/auth/login {табельный №, пароль}──► app
  app: логин заблокирован (5 ошибок)? → 429
       учётка local/test? → сверяем argon2-хэш у нас
       иначе → AuthProvider (сейчас ExternalCheckProvider) ──HTTPS──► внешний сервис: «да/нет»
  ◄── access-токен (JWT, 15 мин) в теле ответа + refresh-токен в cookie HttpOnly; Secure; SameSite=Strict
```
- **AuthProvider** (`backend/app/auth/providers/`) — интерфейс проверки пароля. Переход на SSO (Ory Hydra, этап 7а) — новый адаптер, сессии и RBAC не меняются.
- **Access-токен** живёт только в памяти вкладки (не в localStorage). Через 14 минут фронтенд сам получает новый по refresh-cookie.
- **Refresh-токен** при каждом обновлении меняется (ротация); в БД лежит только его SHA-256. Старый токен минуту ещё принимается (две вкладки), позже — считается украденным, и сессия закрывается.
- **Сессия проверяется на каждом запросе** (одна выборка по первичному ключу): выход, «выйти на всех устройствах» и блокировка администратором действуют сразу, а не через 15 минут.
- **Пароль** нигде не логируется: в запросе он `SecretStr`, в логах только тип ошибки внешнего сервиса. Есть тесты, которые это проверяют.
- **Журнал входов** (`login_events`): успех, неверный пароль, блокировка, сервис недоступен, выход. Вход локальной (аварийной) учёткой дополнительно пишется в `audit_log`.

### RBAC
- Права — в коде (`backend/app/auth/permissions.py`), роли и их галочки — в БД. Навык добавляет своё право `skill.<имя>.use` через `backend/app/skills/registry.py`.
- Итоговые права = «Пользователь» (у всех вошедших) ∪ роли человека ∪ роли его групп. «Администратор» = все права.
- Гостю нельзя выдать ничего, кроме `search.common`: проверка и при сохранении роли, и при каждом расчёте прав (даже если кто-то допишет строку в БД руками).
- Проверка на каждом эндпоинте: `Depends(require_permission("admin.users"))`. Без входа — 401, без права — 403. Тест проходит по всем эндпоинтам админки гостем и обычным пользователем.
- **Защита от повышения прав:** человек с правом `admin.users`, но без роли «Администратор», не может выдать роль «Администратор» и роль с правами, которых нет у него самого (ни напрямую, ни через группу).
- **Последний администратор:** нельзя снять роль, заблокировать или удалить группу, если после этого не останется ни одного активного администратора.
- Все изменения в админке пишутся в `audit_log` (экран журнала — этап 7).

### Фронтенд
Vue 3 + TypeScript + Vite + Pinia + Vue Router + Tailwind 4. Стили компонентов перенесены из согласованных макетов (`frontend/src/styles/main.css`), токены — тот же `design/tokens.css`. Окна и выпадающие меню — Reka UI (доступность: фокус, Esc, aria). Шрифт IBM Plex и иконки собраны в бандл, CDN нет. Собирается в статику внутри образа `proxy`.

## Этап 2: загрузка документов из источника

```
worker (раз в 30 с: «не пора ли?»)
  source_sync ──GET /documents?modified_since=курсор−60 мин──► источник
     │  новые / изменённые → documents.status = queued + задача document_process
     │  удалённые → deleted_at (мягкое удаление), из поиска пропадает
  source_reconcile (ночью и при первом подключении) ──полный список id──► источник
     │  нет у нас или старее → в очередь; нет у источника → missing_in_source
  document_process (по задаче на документ)
     1. GET /documents/{id} → шапка + табличные части + список файлов
     2. staging_documents ← как есть
     3. проверка полноты: строки табличных частей, размер файлов
     4. разбор: PDF (pdfplumber; скан → Tesseract rus+eng), DOCX (python-docx)
     5. одной транзакцией: файлы на диск (/data/documents/ab/<sha256>), фрагменты, ready
```

- **DocumentSource** (`backend/app/sources/`) — интерфейс источника. Адаптер `http_json` говорит на протоколе-допущении ([source-protocol.md](source-protocol.md)); когда придёт настоящий формат функции источника, меняется только адаптер.
- **Идемпотентность.** Документ = `(source_id, external_id)`, версия = дата изменения у источника. Повторно увиденная версия ничего не делает. Задачи по одному документу не дублируются (`jobs.dedupe_key`).
- **Пока документ переобрабатывается, старые фрагменты остаются в поиске.** Замена файлов и фрагментов — одна транзакция в конце.
- **Ошибки** записываются в документ с этапом («Получение», «Проверка полноты», «Парсинг», «OCR») и причиной. 3 попытки с паузой, потом статус «ошибка» и кнопка «Повторить». Если источник не ответил, ничего не удаляется (fail-safe), источник помечается «не отвечает».
- **Возобновление.** Очередь в PostgreSQL, курсор синхронизации сохраняется после каждой страницы, зависшие задачи возвращаются в очередь при старте worker. Первичная индексация после перезапуска продолжается с того же места.
- **Сборка из строк.** Шапка → заголовок «Приказ № 112 от 14.03.2024 «…»» и поля; каждая табличная часть → Markdown-таблица. Это отдельные фрагменты `kind=header`.
- **Нарезка.** Фрагмент не переходит через заголовок раздела, ~1500 символов (не больше 2500). Таблица не режется посередине строки; большая таблица делится по строкам с повтором шапки. У фрагмента хранятся страницы (PDF), раздел и номер пункта — для ссылок на источник в ответе (этап 4). Полнотекстовый индекс с русской морфологией (`chunks.tsv`) строится сразу.
- **Приоритеты очереди:** ручная загрузка 20 > изменения 10 > повтор 5 > первичная индексация 0. Своих обращений к LLM на этом этапе нет; векторизация — этап 4.
- **Общие документы** — из списка `/access/common` источника при каждой синхронизации; у ручных загрузок признак ставит администратор.
- **Админка:** «Источники» (отчёт о полноте, прогноз, ошибки, журнал синхронизаций, токен для API источника), «Коллекции и документы» (реестр с фильтрами, карточка документа: фрагменты, распознанный текст, история, «исключить из поиска», «переиндексировать»), ручная загрузка по праву `documents.upload_manual`.
- **API для источника:** `/api/integration/v1/sources/{код}/documents` — какие его документы загружены и в какой версии. Доступ по токену, у нас хранится только SHA-256.

## Доступ к документам (этап 3)

Права на документы у себя не дублируем: спрашиваем источник по табельному номеру, ответ кэшируем и фильтруем **в SQL, до поиска**.

```
Иванова (10234) открывает «Документы»
  resolve_access()                            backend/app/access/service.py
     access_cache: «Документооборот» спрошен 2 мин назад → свежий, не спрашиваем
                   «Архив ОТ» устарел → GET /access/users/10234   (все устаревшие — параллельно,
                                                                    таймаут ACCESS_TIMEOUT_SECONDS)
        ответил     → access_cache_ids ← список guid (на 5 минут)
        не ответил  → документы «Архива ОТ» скрыты, предупреждение «…сейчас недоступны»
                      (fail-closed; повторно спросим через ACCESS_RETRY_SECONDS)
  visible(access)                             backend/app/access/filters.py
     документ жив (не удалён, не исключён, обработан) И (
        общий
        ИЛИ источник ответил и guid документа есть в access_cache_ids человека
        ИЛИ ручная загрузка, открытая человеку или его группе (document_grants) )
```

- **Где применяется фильтр:** список документов и значения фильтров, карточка, текст по фрагментам, скачивание файла. Поиск, граф и противоречия (этапы 4–6) обязаны строить запросы через тот же `visible()`. Прямая ссылка на чужой документ даёт 403 «Нет доступа к документу», гостю — «Документ доступен только после входа», при недоступном источнике — 503 «Документы из системы X сейчас недоступны».
- **Кто что видит.** Гость — только общие документы (право `search.common`). Вошедший с правом `documents.view` — общие + разрешённые источником + открытые ему ручные загрузки. Без `documents.view` — только общие. Роль «Администратор» права на документы не даёт: их даёт источник. Админка (`/api/admin/documents`) — отдельный отладочный раздел и права источника не учитывает (вопрос 15).
- **Кэш прав** (`access_cache` + `access_cache_ids`) — в PostgreSQL, а не в памяти процесса: фильтр — это `EXISTS` по первичному ключу прямо в SQL-запросе, кэш общий для всех процессов `app`, сброс работает сразу везде. Сбрасывается при входе человека и кнопкой «Сбросить кэш прав» в админке («Источники»).
- **Общие документы при недоступном источнике остаются видны:** признак «общий» уже лежит в нашем реестре (обновляется при синхронизации), спрашивать источник для них не нужно.
- **Ручные загрузки:** загрузивший видит документ сразу; администратор открывает его людям (по табельному номеру, даже если человек ещё не входил) и группам в карточке документа.

## Поиск и чат (этап 4)

Подробно, с примерами: [search.md](search.md).

- **Гибридный поиск в PostgreSQL:** векторы bge-m3 (`chunks.embedding vector(1024)`, HNSW-индекс) + полнотекстовый (`chunks.tsv`, русская морфология), слияние RRF. Отдельная векторная БД не нужна: права фильтруются тем же `visible(access)` в том же SQL-запросе.
- **Реранкер** bge-reranker-v2-m3 — в контейнере `app` через onnxruntime на CPU (int8); видеопамять остаётся модели и эмбеддингам.
- **Ответ потоком (SSE)** с этапами («найдено», «в очереди», «пишу ответ»), источниками и heartbeat.
- **Очередь к модели** (`llm_queue`) с местом в очереди; пока в ней кто-то есть, worker не векторизует и не обращается к LLM.
- **История чатов** вошедших — 90 дней; у гостя — только в браузере.
- **Фейковая Ollama** (`backend/fakes/fake_ollama.py`) — тесты и CI без видеокарты.
