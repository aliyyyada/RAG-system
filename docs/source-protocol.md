# Источник документов

Сейчас на заводе один источник — **функция в Microsoft SQL Server** (адаптер `mssql`,
`backend/app/sources/mssql.py`). Ниже — как мы её вызываем и что ждём в ответ. Во второй
части — наш первоначальный HTTP-протокол (адаптер `http_json`): на нём работают фейковые
источники в тестах, и его можно предложить второй системе, если она будет отдавать данные
по HTTPS. Синхронизация, проверки полноты и отчёт работают через интерфейс `DocumentSource`
и от адаптера не зависят.

# Часть 1. Функция в MS SQL Server (адаптер `mssql`)

Формат подтверждён скриншотом и ответами разработчиков источника 02.11.2026: у функции
нет параметров, она отдаёт все документы, вход — по SQL-логину, файлы — doc, pdf, tiff,
даты изменения и удаления источник добавит позже. Что ещё неизвестно, собрано
в [open-questions.md](open-questions.md) (вопросы 33, 34, 36, 37); всё это задаётся
в настройках источника.

## Подключение

- Адрес источника: `mssql://сервер:1433/База`.
- Логин SQL Server **только на чтение**: `SOURCE_MSSQL_USER` и `SOURCE_MSSQL_PASSWORD` в `.env`.
  Пароль не хранится в базе, не показывается в интерфейсе и не пишется в журналы.
- Соединение шифруется (TLS), сертификат сервера проверяется по `SOURCE_CA_FILE`.
- Драйвер — python-tds (MIT, чистый Python): не нужен ODBC-драйвер Microsoft.

## Что возвращает функция

Вызов (по умолчанию `EXEC dbo.GetDocuments`, меняется в настройках) возвращает две таблицы.
Какая из них какая, определяем по колонкам, а не по порядку.

**1. Метаданные документов**

| Колонка | Пример | У нас |
|---------|--------|-------|
| ID_GUID | `9F7248C8-BEDC-4103-A896-F89E687A28BF` | id документа в источнике (сравниваем без учёта регистра) |
| ID_Вид | `1` | техническое поле `_ID_Вид`: не в поиске, не в карточке |
| ID_Key | `17` | техническое поле `_ID_Key` |
| Номер | `537к` | номер документа |
| Дата | `2011-05-12 00:00:00.000` | дата документа |
| Тип | `ПРИКАЗ` | вид документа («Приказ») |
| Тема | `О допуске персонала…` | название документа |
| Исполнитель | `Иванова А. С.` | реквизит «Исполнитель», попадает в текст для поиска |

Любая новая колонка попадёт в текст документа с исходным именем без доработки кода.
Соответствие колонок задаётся в настройках (`header_map`, `hidden_columns`).

**2. Бинарники**

| Колонка | Пример | У нас |
|---------|--------|-------|
| ID_GUID | тот же, что в первой таблице | к какому документу файл |
| BinaryFile | `0x255044462D…` (PDF) | содержимое файла |
| тип файла (имя уточняется) | `pdf` | подсказка; тип определяем по содержимому |

Строк с одним ID_GUID может быть несколько — у документа будет несколько файлов. Файл без
строки в первой таблице пропускается (пишется в журнал). Пустой `BinaryFile` — ошибка
«Проверка полноты» у документа. Имя файла строим из вида и номера: `приказ_537к.pdf`.

Поддерживаемые файлы: PDF (текстовый слой или скан → OCR), старый Word `.doc` (Word 97–2003),
DOCX, сканы-картинки TIFF (в том числе многостраничные), PNG, JPEG → OCR постранично.

`.doc` разбираем сами (`backend/app/ingest/doc.py`): контейнер OLE открывает olefile (BSD),
а текст, заголовки (стили «Заголовок 1–5») и таблицы читаются по открытой спецификации
Microsoft [MS-DOC]. Конец строки таблицы берётся из свойств абзаца, поэтому пустые ячейки
не сдвигают столбцы. Не поддерживаются .doc, защищённые паролем (понятная ошибка), и
картинки внутри .doc (сканы, вклеенные в Word, не распознаются).

## Как находим изменения: снимок и отпечатки

Даты изменения и удаления у источника нет, а все бинарники приходят одним вызовом. Поэтому:

1. Вызываем функцию. Метаданные держим в памяти, бинарники по одному пишем в хранилище
   файлов (имя = SHA-256 содержимого, одинаковый файл хранится один раз).
2. Для каждого документа считаем **отпечаток** = SHA-256(метаданные + хэши файлов) и пишем
   в таблицу `source_items`.
3. Отпечаток изменился → версия документа = время этого вызова → документ встаёт в очередь
   на переиндексацию. Не изменился → версия прежняя, документ не трогаем.
4. Документа нет в полном ответе функции → он удалён в источнике и пропадает из поиска.
   Если функция не ответила или ответила ошибкой, ничего не удаляется.

Пример: сегодня функция вернула приказ «537к» с PDF, завтра — тот же приказ с другим PDF.
Отпечаток другой, приказ переиндексируется. Остальные документы не трогаются.

Полный вызов дорогой (все файлы сразу), поэтому синхронизация раз в час берёт свежий снимок
не чаще раза в 6 часов (`full_refresh_minutes`), а ночная сверка — всегда. Если источник
добавит колонки даты изменения и удаления или параметр «изменено после», это включается
в настройках без переделки кода (`modified_column`, `deleted_column`, `:since` в вызове).

## Права на документы

Без входа документы не видит никто, даже общие. Для вошедших — режим в настройках источника:

- **«Любой вошедший видит все документы источника»** (`all_authenticated`, по умолчанию;
  подтверждено 02.11.2026: функция отдаёт все документы, отдельных прав у источника нет).
- **«Спрашивать источник по табельному номеру»** (`sql`): вызываем «Запрос прав», например
  `EXEC dbo.GetUserDocuments @Login = :user`, где `:user` — табельный номер. Ответ — таблица
  с колонкой ID_GUID. Кэш 5 минут, источник не ответил — его документы скрыты (fail-closed).

Общие документы — необязательный «Запрос общих документов» (ответ — колонка ID_GUID).

## Настройки источника (`sources.config`)

| Поле | По умолчанию | Что это |
|------|--------------|---------|
| `call_sql` | `EXEC dbo.GetDocuments` | вызов функции; можно `:user`, `:since`. Только один вызов `EXEC`/`SELECT`, без «;» |
| `service_user` | — | значение `:user` при синхронизации |
| `id_column`, `binary_column` | `ID_GUID`, `BinaryFile` | ключевые колонки |
| `file_type_column`, `file_name_column` | угадываем / — | колонки типа и имени файла |
| `header_map` | Номер→number, Дата→date, Тип→doc_type, Тема→title, Исполнитель→executor | соответствие колонок |
| `hidden_columns` | `ID_Вид`, `ID_Key` | не показывать и не искать |
| `modified_column`, `deleted_column` | — | если источник добавит даты |
| `access_mode`, `access_sql` | `all_authenticated`, — | права (см. выше) |
| `common_sql` | — | список общих документов |
| `full_refresh_minutes` | 360 | как часто брать полный снимок вне ночной сверки |
| `encrypt` | `true` | шифровать соединение |
| `credentials_env` | `SOURCE_MSSQL` | префикс переменных `.env` с логином и паролем |

Для разработки есть фейковый источник без SQL Server: `python -m app.cli seed-fake-mssql`
(таблицы из `backend/fakes/fake_mssql.py`).

# Часть 2. Протокол HTTP + JSON (адаптер `http_json`)

Наш первоначальный протокол, придуманный до получения настоящего формата. Его понимает
адаптер `http_json` (`backend/app/sources/http_json.py`), на нём говорит фейковый источник
(`backend/fakes/fake_source.py`).

Все запросы — `GET` по HTTPS, ответы — JSON в UTF-8. Даты — ISO 8601 **с часовым поясом**
(`2024-05-20T08:42:00+03:00`). Адрес API задаётся в настройках источника, например
`https://docflow.zavod.local/api/rag`.

## 1. Список документов

```
GET {адрес}/documents?modified_since=2026-10-31T10:00:00+03:00&cursor=<…>&limit=500
```

- `modified_since` — только документы, изменённые не раньше этой даты (инкрементальная
  синхронизация, каждые 15 минут). Без параметра — **все** документы, включая удалённые
  (ночная сверка).
- Порядок — по дате изменения, затем по id. `cursor` — непрозрачная строка из предыдущего ответа.

```json
{
  "items": [
    {"id": "5ef9…dbc5", "modified_at": "2024-05-20T08:42:00+00:00", "deleted_at": null},
    {"id": "1a2b…9f00", "modified_at": "2021-01-01T00:00:00+00:00", "deleted_at": "2021-01-01T00:00:00+00:00"}
  ],
  "next_cursor": "500"
}
```

`deleted_at` не пустой — документ мягко удалён в источнике, у нас он пропадает из поиска.

## 2. Документ целиком

```
GET {адрес}/documents/{id}
```

```json
{
  "header": {
    "id": "5ef9…dbc5",
    "modified_at": "2024-05-20T08:42:00+00:00",
    "deleted_at": null,
    "doc_type": "Приказ",
    "number": "112",
    "date": "2024-03-14",
    "title": "О допуске персонала к работам на высоте",
    "topic": "Охрана труда",
    "department": "Служба ОТ и ПБ",
    "любое другое поле": "попадёт в текст документа как «любое другое поле: …»"
  },
  "parts": [
    {
      "name": "Ознакомлены",
      "row_count": 46,
      "rows": [
        {"document_id": "5ef9…dbc5", "personnel_number": "20871", "full_name": "Петров В. Н.", "acquainted_at": "2024-03-15"}
      ]
    }
  ],
  "files": [
    {"id": "f-001", "name": "prikaz_112.pdf", "size": 51692, "mime": "application/pdf"}
  ]
}
```

- `parts[].row_count` — сколько строк **должно** быть. Не совпало с числом в `rows` —
  ошибка «Проверка полноты», документ не загружается, пока источник не дошлёт все строки.
- `files[].size` — размер в байтах. Не совпал со скачанным — та же ошибка.
- 404 — документа больше нет (у нас помечается удалённым).

## 3. Файл

```
GET {адрес}/files/{id файла}     → байты файла (PDF или DOCX)
```

Тип определяется по содержимому, а не по расширению. Больше `SOURCE_FILE_MAX_MB` (200 МБ) не скачиваем.

## 4. Общие документы

```
GET {адрес}/access/common         → {"ids": ["…", "…"]}
```

Документы из этого списка доступны всем вошедшим (без входа документов не видит никто).

## 5. Права пользователя на документы

```
GET {адрес}/access/users/{табельный номер}   → {"ids": ["…", "…"]}
```

- Список guid документов, которые источник разрешает этому человеку. На одного человека
  может прийти несколько тысяч id — это нормально (≈ 200 КБ JSON на 5 000 id).
- 404 — источник не знает такого человека: у него нет прав на документы источника (не ошибка).
- Таймаут (`ACCESS_TIMEOUT_SECONDS`, 5 с), ответ не 200/404 или не JSON — «источник не отвечает»:
  документы этого источника человеку не показываем (fail-closed), он видит предупреждение
  «Документы из системы X сейчас недоступны». Повторно спрашиваем через `ACCESS_RETRY_SECONDS` (30 с).
- Ответ кэшируется на `ACCESS_CACHE_MINUTES` (5 минут), кэш сбрасывается при входе человека
  и кнопкой в админке. Общие документы (раздел 4) сюда включать не обязательно.

## Ошибки и доступность

Таймаут (`SOURCE_TIMEOUT_SECONDS`, 30 с), ответ не 200/404 или не JSON — «источник не отвечает»:
синхронизация записывает ошибку в журнал, ничего не удаляет и повторяется по расписанию.

## Обратный API: что у нас загружено

Источник может спросить нас (токен выпускает администратор на странице источника):

```
GET  https://<наш сервер>/api/integration/v1/sources/docflow/documents?cursor=&limit=1000
POST https://<наш сервер>/api/integration/v1/sources/docflow/documents/lookup   {"ids": ["…"]}
Authorization: Bearer src_docflow_…
```

По каждому документу: `source_version` (последняя версия, которую мы видели), `indexed_version`
(версия, которая сейчас в поиске), `status` (`queued`, `processing`, `ready`, `error`, `deleted`,
`unknown`) и текст ошибки.
