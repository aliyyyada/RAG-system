# Видеокарта и память: почему так и как проверить

Два вопроса, которые возникают на первой большой загрузке документов:

1. Почему при загрузке и обработке документов видеокарта занята всего на 10–20 %?
2. Почему расход оперативной памяти растёт до ~20 ГБ и не уменьшается?

Ниже — что происходит на самом деле, команды для проверки (PowerShell на сервере) и что
настроить.

---

## 1. Видеокарта загружена на 10–20 %

### Что происходит

Загрузка одного документа — это цепочка шагов, и видеокарта участвует только в одном из них:

| Шаг | Чем выполняется | Сколько длится (примерно) |
|---|---|---|
| Скачать запись и файлы из источника | сеть, MS SQL | доли секунды |
| Разобрать PDF/DOCX (текст, таблицы) | **процессор**, одно ядро | 1–10 с на файл |
| Распознать скан (OCR, Tesseract) | **процессор** | 5–20 с на страницу |
| Нарезать на фрагменты, сохранить | процессор, PostgreSQL | доли секунды |
| Векторизовать фрагменты (bge-m3) | **видеокарта** | ~0,5–1 с на 32 фрагмента |

То есть видеокарта отрабатывает за секунду то, что процессор готовил 10–60 секунд, и
остальное время ждёт. Средняя загрузка 10–20 % при индексации — это ожидаемо: узкое место —
процессор (i3-12100, 4 ядра), а не видеокарта.

Полностью видеокарта загружается только там, где модель **пишет текст**: ответ в чате,
извлечение графа моделью, проверка противоречий, проверка ЕПоЗ с моделью. Там должно быть
80–100 %.

Что было исправлено в коде (PR «Разбор в отдельном процессе…»):

- раньше worker делал всё строго по очереди: пока разбирался PDF, видеокарта стояла;
  теперь у worker'а две «полосы»: процессорная (синхронизация, разбор, OCR) и
  видеокарточная (векторизация, граф, противоречия, ЕПоЗ). Пока разбирается следующий
  документ, фрагменты предыдущего уже векторизуются. Фоновый запрос к модели по-прежнему
  идёт не больше одного за раз, а вопросы пользователей всё так же идут первыми;
- векторизация пачками по 32 фрагмента вместо 16, векторы пачки записываются одной командой.

### Как проверить

**Диспетчер задач Windows обманывает.** На вкладке «Производительность → ГП» по умолчанию
показан график «3D», а вычисления Ollama идут через CUDA и туда не попадают. Либо переключите
один из графиков на «Cuda» / «Compute_0», либо смотрите `nvidia-smi`:

```powershell
# Загрузка видеокарты и видеопамять раз в секунду (Ctrl+C — выход)
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 1
```

**Главная проверка — модель целиком на видеокарте?**

```powershell
docker compose exec ollama ollama ps
```

В колонке `PROCESSOR` должно быть `100% GPU` у обеих моделей (qwen2.5 и bge-m3). Если там,
например, `25%/75% CPU/GPU` — часть модели не поместилась в 8 ГБ и считается на процессоре.
Тогда и видеокарта простаивает (ждёт процессор), и оперативная память контейнера ollama растёт
на несколько гигабайт. То же видно в журнале:

```powershell
docker compose logs ollama | Select-String "offloaded"
# хорошо: offloaded 29/29 layers to GPU
```

Что делать, если модель не помещается:

1. Уменьшить контекст: в `.env` `LLM_NUM_CTX=4096` (вместо 8192), затем
   `docker compose up -d app worker`. Каждые 4096 токенов контекста у qwen2.5:7b — это
   примерно 0,25 ГБ видеопамяти плюс рабочие буферы.
2. Закрыть на сервере программы, которые занимают видеопамять (браузер с аппаратным
   ускорением, удалённый рабочий стол с большим разрешением): `nvidia-smi` без параметров
   показывает, сколько памяти занято чужими процессами.
3. Временно работать на запасной модели `qwen3:4b` (`LLM_MODEL=qwen3:4b`).

**Чем занят worker прямо сейчас** — очередь задач:

```powershell
docker compose exec postgres psql -U rag -d rag -c "SELECT kind, status, count(*) FROM jobs GROUP BY 1, 2 ORDER BY 1, 2"
```

Много `parse_document` в `queued` и мало `chunk_embed` — узкое место процессор (так и должно
быть при первичной загрузке). Скорость векторизации — выполните два раза с интервалом в минуту
и сравните второе число:

```powershell
docker compose exec postgres psql -U rag -d rag -c "SELECT count(*) AS fragments, count(embedding) AS vectorized FROM chunks"
```

## 2. Оперативная память растёт до 20 ГБ

### Откуда берутся 20 ГБ

Сложите лимиты контейнеров из `docker-compose.yml`:

| Контейнер | Лимит | Что там живёт |
|---|---|---|
| ollama | 12 ГБ | веса моделей проходят через память при загрузке; если модель не влезла в видеокарту — её часть живёт здесь постоянно |
| worker | 4 ГБ | разбор PDF и OCR сканов |
| app | 4 ГБ | реранкер (~1 ГБ) |
| postgres | 4 ГБ | кэш базы (`shared_buffers=1GB`) — заполняется и так и остаётся, это нормально |

Итого до 24 ГБ. Плюс Docker Desktop работает внутри виртуальной машины WSL2 (в диспетчере
задач — процесс **Vmmem** или **VmmemWSL**), а она **кэширует прочитанные файлы** (модели
~6 ГБ, документы, файлы базы) и по умолчанию **не возвращает эту память Windows**, даже когда
контейнерам она уже не нужна. Поэтому в Windows видно «съело 20 ГБ и не отдаёт».

Отдельная настоящая проблема была в worker'е: при разборе больших PDF pdfplumber держал в
памяти все страницы файла до конца разбора, а Python почти не возвращает системе память,
освободившуюся после больших сканов. Worker постепенно «толстел» до своего лимита 4 ГБ.
Исправлено в коде:

- каждая страница PDF освобождается сразу после разбора;
- разбор файлов идёт в отдельном процессе, который после 20 файлов (`PARSE_TASKS_PER_PROCESS`)
  заменяется новым — вся его память гарантированно возвращается;
- если процесс разбора убит из-за нехватки памяти (огромный скан), документ получает понятную
  ошибку и кнопку «Повторить», а worker продолжает работу;
- `MALLOC_ARENA_MAX=2` в `docker-compose.yml` — Python меньше «раздувается» от работы в потоках.

### Как проверить

```powershell
# Сколько памяти занимает каждый контейнер прямо сейчас
docker stats --no-stream
# Процессы внутри worker'а (видно процесс разбора и его память в колонке RSS)
docker compose top worker
```

- Растёт `rag-worker-1` и упирается в 4 ГБ — это та проблема, что исправлена в коде.
- `rag-ollama-1` занимает больше 2–3 ГБ — модель частично на процессоре (см. `ollama ps` выше).
- Контейнеры в сумме занимают, скажем, 9 ГБ, а Vmmem в диспетчере задач — 20 ГБ: разница —
  это файловый кэш WSL2, лечится настройкой ниже.

### Настройка WSL2: ограничить и возвращать память

Создайте (или откройте) файл `C:\Users\<имя пользователя>\.wslconfig` в Блокноте:

```ini
[wsl2]
# Сколько памяти максимум может взять Docker (из 32 ГБ сервера)
memory=24GB

[experimental]
# Постепенно возвращать Windows память, которую Linux держит под кэш файлов
autoMemoryReclaim=gradual
```

Затем полностью перезапустите WSL (контейнеры остановятся и поднимутся вместе с Docker Desktop):

```powershell
wsl --shutdown
# и снова запустить Docker Desktop
```

`autoMemoryReclaim` работает с WSL версии 2.0 и новее. Проверить версию: `wsl --version`
(если команда не найдена — WSL старый, встроенный в Windows, и эта строка ни на что не
влияет; лимит `memory=` работает всегда). Освободить кэш вручную, не перезапуская ничего:

```powershell
wsl -d docker-desktop sh -c "echo 1 > /proc/sys/vm/drop_caches"
```

## Краткая памятка

| Симптом | Команда | Норма | Если не так |
|---|---|---|---|
| Видеокарта 10–20 % при загрузке документов | `nvidia-smi ... -l 1` | всплески при векторизации | норма: ждёт процессор (разбор, OCR) |
| Видеокарта низкая во время ответа в чате | `ollama ps` | `100% GPU` | уменьшить `LLM_NUM_CTX`, освободить видеопамять |
| Растёт память worker | `docker stats` | до ~1,5 ГБ, после разбора падает | обновить код (разбор в отдельном процессе) |
| Vmmem держит память | диспетчер задач | ≈ сумма `docker stats` + кэш | `.wslconfig`: `memory=`, `autoMemoryReclaim` |
