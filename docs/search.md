# Поиск и ответы (этап 4)

## Путь вопроса

```
Браузер ──POST /api/chat/ask {вопрос, фильтры, chat_id}──► app        (ответ — поток SSE)
  1. Права: resolve_access() — тот же кэш прав источников, что у «Документов» (этап 3)
  2. Вектор вопроса: Ollama, bge-m3                           ~50 мс на GPU
  3. Гибридный поиск в PostgreSQL, ОБА запроса с условием visible(access):
       векторный   — HNSW-индекс pgvector, косинусное расстояние, 30 лучших
       полнотекст  — tsvector с русской морфологией, слова через ИЛИ, ts_rank_cd, 30 лучших
       RRF         — score = Σ 1/(60 + место); 20 лучших идут дальше
  4. Реранкер bge-reranker-v2-m3 (onnxruntime, CPU): оценка 0…1 каждой паре «вопрос — фрагмент»;
     ниже 0,05 отбрасываем, берём 6 лучших                    ~2–4 с на CPU (оценка)
  5. Ничего не осталось? → «В доступных вам документах ответа на этот вопрос нет.» Модель не нужна.
  6. Очередь к модели (llm_queue): «вы 2-й в очереди»; вошедшие — раньше гостей
  7. qwen2.5:7b по промпту «отвечай только по фрагментам, ставь [n]» — ответ по кусочку
  8. Ответ, источники и время — в историю чата; в аудит — вопрос и какие документы попали в ответ
```

Код: `backend/app/search/` (поиск, реранкер, векторизация), `backend/app/chat/` (ответ, промпт, очередь, история), `backend/app/api/chat.py` (эндпоинты).

### Почему гибридный

| Вопрос | Полнотекстовый | Векторный |
|--------|---------------|-----------|
| «приказ 112», «ИОТ-044», «КМ-104» | находит точно (номер — это слово) | номера и шифры «по смыслу» путает |
| «сколько действует наряд» (в тексте — «выдаётся на срок не более 15 дней») | не находит: слов «действует» нет | находит: смысл тот же |
| «электросварщиков» | находит «электросварщик» (русская морфология) | находит |

RRF складывает не оценки (они несравнимы: косинусное расстояние и ts_rank), а места в списках. Фрагмент, который на 2-м месте в обоих списках, обгонит фрагмент, который на 1-м месте только в одном.

### Права — до поиска

Условие `visible(access)` (`backend/app/access/filters.py`) стоит **внутри** обоих SQL-запросов. Фрагмент закрытого документа не попадает ни в кандидаты, ни в реранкер, ни в промпт модели. Тест `test_answer_streams_with_sources_and_citations` проверяет, что текст закрытого для T-0001 приказа № 45 («…главного инженера Смирнова…») не встречается ни в одном промпте фейковой Ollama. Отрывки и реквизиты для источников загружаются вторым запросом — снова с `visible(access)`: между поиском и ответом кэш прав мог обновиться.

HNSW-индекс ищет ближайшие векторы, а условие прав отбрасывает чужие. Чтобы после отбрасывания осталось 30 кандидатов, включён `hnsw.iterative_scan` (pgvector 0.8): индекс продолжает поиск, пока не наберёт нужное число разрешённых.

### Многошаговый диалог

На уточнение «а на какой срок он выдаётся?» поиск по одной этой фразе найдёт что угодно. Поэтому ищем дважды — по вопросу и по «предыдущий вопрос + вопрос» — и сливаем тем же RRF. Модель получает последние 6 реплик диалога (`CHAT_HISTORY_TURNS`). Переписывать вопрос моделью («сделай самостоятельный вопрос») не стали: это ещё один вызов LLM на 3–5 с на каждый вопрос.

### Векторизация

После разбора документа worker ставит задачу `chunk_embed`: по 16 фрагментов за запрос к Ollama. В вектор идёт фрагмент вместе с названием документа и разделом («Приказ № 112 «О допуске…» / 4. Порядок допуска / 4.2. Допуск осуществляется…»), иначе фрагмент «4.2. Допуск осуществляется по наряду…» теряет контекст. Пока документ не векторизован, он находится полнотекстовым поиском. Фрагменты без вектора (например, загруженные до этапа 4) worker находит сам раз в 30 секунд.

**Пользователи важнее.** Перед каждой пачкой worker проверяет, не ждёт ли кто-нибудь ответа (идёт генерация или есть живая запись в `llm_queue`). Ждёт — задача откладывается на 5 секунд без траты попытки. Ollama не отвечает — откладывается на минуту.

### Реранкер

Ollama реранкеры не запускает, поэтому bge-reranker-v2-m3 (Apache-2.0) работает в контейнере `app` через onnxruntime на CPU (решение по open-questions #11). Модель квантована в int8 (~570 МБ). Её готовит `scripts/offline/export-reranker.sh` на машине с интернетом, офлайн-установщик кладёт её в том `rag_reranker_model`. Нет модели — поиск работает без реранкера (порядок RRF) и пишет предупреждение в журнал.

Порог `RERANK_MIN_SCORE=0.05`: если ни один фрагмент не набрал хотя бы 5 %, система сразу отвечает «ответа нет», не обращаясь к модели. Так вопрос «сколько стоит абонемент в бассейн» не тратит 10 секунд видеокарты.

### Промпт и честный отказ

`backend/app/chat/prompt.py`. Правила для модели: только сведения из фрагментов; после каждого утверждения номер `[n]`; нет ответа — ровно фраза «В доступных вам документах ответа на этот вопрос нет.»; вопрос не о документах («2+2») — «Я отвечаю только на вопросы по документам предприятия.»; отменённый документ — предупредить. Текст фрагментов помечен как данные: команды внутри документа модель выполнять не должна.

### Поток ответа (SSE)

| Событие | Когда | Что показывает интерфейс |
|---------|-------|--------------------------|
| `meta` | сразу | id чата (адрес `/?chat=7`), недоступные источники |
| `status` | этапы | «Найдено 14 фрагментов», «Отобрано 5 лучших», «Ожидание модели: вы 2-й в очереди» |
| `sources` | до ответа | источники справа: документ, статус, место, отрывок с подсветкой |
| `token` | по кусочку | текст ответа с номерами `[n]` |
| `done` | в конце | какие источники процитированы, время ответа |
| `error` | ошибка | «Модель сейчас недоступна» — найденные фрагменты при этом остаются видны |
| `: ping` | каждые 2 с тишины | ничего: держит соединение (Windows рвёт тихие соединения) |

Клик по номеру `[n]` подсвечивает источник справа, клик по источнику открывает `/documents/{id}?chunk={id}` — документ прокручен к фрагменту, фрагмент выделен. «К ответу» возвращает в тот же диалог.

### Очередь к модели

Видеокарта одна, Ollama отвечает по одному (`OLLAMA_NUM_PARALLEL=1`). Каждый ответ записывается в `llm_queue`; место = сколько живых записей впереди. Вошедшие пользователи идут раньше гостей, начатый ответ не прерывается. Запись «жива», пока её поток раз в 5 секунд обновляет `heartbeat_at`: если процесс упал, через 30 секунд очередь о ней забывает.

### История

- Вошедшие: чаты в `chats` / `chat_messages`, слева список «Сегодня / Вчера / Ранее» и поиск по истории. Удаляются через `CHAT_HISTORY_DAYS` (90) дней после последнего вопроса.
- Если права на документ отозваны, в старом ответе источник показывается как «Документ сейчас недоступен» — без названия и отрывка (open-questions #23).
- Гость: история только в браузере (localStorage), сервер её не хранит; в аудит пишутся IP, время и вопрос. Не больше 6 вопросов в минуту с одного IP (`GUEST_QUESTIONS_PER_MINUTE`).

### Фильтры

Источник, коллекция, тип документа, дата, «Только действующие». До этапа 5 «действует / отменён» берётся из поля `status` шапки источника; на этапе 5 статус будет вычисляться по связям «отменяет / изменяет».

## Оценка качества (recall@k)

`backend/eval/questions.json` — 34 вопроса по тестовым документам с ожидаемыми номерами документов. Запуск:

```bash
docker compose exec app python -m app.cli eval-search --file eval/questions.json
```

Выводит recall@1/3/5/10 (доля ожидаемых документов в первых k найденных), MRR и список промахов. Запускайте до и после изменения поиска (размер фрагмента, реранкер, число кандидатов). Тест `test_recall_on_eval_set` требует recall@5 ≥ 0,9 на фейковых эмбеддингах; сейчас 1,0 (recall@1 = 0,82, MRR = 0,93).

Для документов завода нужен такой же файл с 30–50 реальными вопросами сотрудников (open-questions #22): фейковые документы показывают, что механизм работает, но не качество на настоящих приказах.

## Тесты без видеокарты

`backend/fakes/fake_ollama.py` — фейковая Ollama с тем же HTTP API: эмбеддинги — хэш основ слов в 1024 координаты, ответ — самое подходящее предложение из фрагментов со ссылкой `[n]`. В CI она поднимается внутри фейкового сервиса (`OLLAMA_URL=http://localhost:11434/ollama`). Тесты (`backend/tests/test_search_chat.py`, 21 тест) проверяют права в поиске, в источниках, в промпте и в истории; heartbeat при молчащей модели; отказ на вопросы не по теме; очередь и приоритет гостей; ограничение частоты для гостей; отложенную векторизацию, пока пользователь ждёт. Обвязку реранкера проверяет игрушечная ONNX-модель (`test_rerank_onnx.py`).

## Замеры на сервере (сделать при установке)

| Что | Оценка до замера | Как замерить |
|-----|------------------|-------------|
| Вектор вопроса (bge-m3, GPU) | 30–80 мс | `scripts/bench/ollama_bench.py` |
| Реранкер, 20 фрагментов (CPU, int8) | 2–4 с | время `rerank` в `meta.timings_ms` ответа (история чата) |
| Первый токен qwen2.5:7b | 1–3 с при 6 фрагментах | `scripts/bench/ollama_bench.py` |
| Скорость ответа | 25–35 токенов/с на GTX 1070 | `meta.tokens_per_second` |

Если реранкер на CPU окажется медленнее 4 секунд, уменьшить `RERANK_TOP_N` до 10–12 или выключить (`RERANKER=none`) и сравнить recall@5.
