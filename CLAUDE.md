Ты ведущий разработчик и архитектор. Мы с нуля и основательно строим корпоративную систему поиска и ответов по документам предприятия (RAG). Есть прототип (FastAPI + SQLite + Ollama), но новый проект пишем заново, с нормальной архитектурой, тестами и безопасностью. ## 2. Жёсткие ограничения среды

- **Полностью офлайн.** На заводе нет интернета. Все Docker-образы, модели Ollama, pip- и npm-зависимости, шрифты и иконки должны собираться в офлайн-пакет заранее: скрипт сборки на машине с интернетом и скрипт установки на заводе. Никаких CDN, Google Fonts или внешних API в рантайме.
- **Сервер:** Windows + Docker Desktop (WSL2). CPU i3-12100, RAM 32 ГБ, GPU **NVIDIA GeForce GTX 1070, 8 ГБ VRAM** (Pascal, драйвер 472.12, Ollama на нём работает). Все модели должны работать **на видеокарте**.
- **Windows обрывает простаивающие HTTP-соединения** через несколько секунд. Все долгие ответы отдаются потоком (SSE) с heartbeat не реже чем раз в 2–3 секунды.
- **HTTPS везде, включая разработку.** Сертификат дадут админы предприятия (внутренний CA). Для локальной разработки до его получения используем самоподписанный сертификат. Обычный HTTP запрещён, порт 80 только редиректит на 443.
- **Лицензии:** только допускающие коммерческое использование (Apache-2.0, MIT, BSD). Например, Qwen2.5-3B не подходит (лицензия Qwen Research), а Qwen2.5-7B и Qwen3 подходят (Apache-2.0). Проверяй лицензию каждой модели и библиотеки.
- **На предприятии запрещено писать код на Java и Go.** Свой код пишем только на Python (backend) и TypeScript (frontend). Готовые программы на этих языках использовать можно (Ollama, Docker, nginx и т. п.), но только если для них не нужно ничего дописывать на Java/Go (плагины, расширения).
- Один сервер, без Kubernetes. Всё поднимается одним `docker compose up`.

## 3. Рекомендуемый стек (можешь возразить с аргументами)

- **Backend:** Python 3.12, FastAPI, SQLAlchemy + Alembic (миграции), Pydantic.
- **БД:** PostgreSQL 16 + **pgvector** (векторы) + встроенный полнотекстовый поиск с русской морфологией. В той же БД лежат пользователи, роли, документы, граф знаний и журнал аудита. Отдельная векторная БД, MinIO и Redis не нужны, пока не доказано обратное.
- **Файлы документов** хранятся на диске (том Docker), имя файла = хэш содержимого.
- **Фоновые задачи** (синхронизация, парсинг, векторизация, построение графа, поиск противоречий) выполняет отдельный worker-контейнер с очередью в PostgreSQL. **Запросы пользователей всегда в приоритете:** пока пользователь ждёт ответ, фоновые задачи к LLM не обращаются.
- **LLM:** Ollama. Основная модель `qwen2.5:7b-instruct` (Q4_K_M), запасная `qwen3:4b`. Эмбеддинги `bge-m3`. Реранкер `bge-reranker-v2-m3`. Используется **одна LLM**: две модели по 7–8B вместе с bge-m3 в 8 ГБ не помещаются, а переключение между ними занимает 5–15 секунд. Перед выбором замерь на нашем GPU реальный расход VRAM и скорость (токенов в секунду) и подбери `num_ctx`. Лимит памяти контейнера ollama подними под 7B-модель.
- **Frontend:** **Vue 3** (Composition API, `<script setup>`) + TypeScript + Vite + Pinia + Vue Router + Tailwind CSS + библиотека компонентов для Vue (shadcn-vue или PrimeVue, выбери и обоснуй). Собирается в статику, которую отдаёт reverse proxy. Шрифты и иконки лежат локально. React не используем.
- **Reverse proxy:** nginx, TLS с сертификатом из папки `certs/`.
- **Тесты:** pytest (юнит + e2e с фейковым Ollama и фейковым внешним сервисом), Playwright для основных сценариев UI.

## 4. Пользователи и вход

- Пользователей **не регистрируем у себя**. Они уже есть во внешнем сервисе пользователей. Общий ключ пользователя во всех системах — **табельный (личный) номер**, он уникален.
- **Отдельная страница входа** обязательна, на неё ведёт кнопка «Войти» в шапке. **Без входа (гостевой режим)** можно задавать вопросы и просматривать только **общие документы, доступные всем** (см. п. 6). Всё остальное (документы по правам, противоречия, навыки, админка) открывается только после входа.
- **Сейчас (решено):** наша страница входа отправляет логин и пароль в функцию проверки внешнего сервиса (вариант 4 ниже) по HTTPS. Пароль нигде не логируется и не хранится.
- **Позже (план):** админы хотят единый вход (SSO) для всего предприятия. Keycloak не подходит: чтобы он проверял пароли через внешний сервис, нужно писать плагин на Java. Используем **Ory Hydra** (готовая программа, Apache-2.0, офлайн Docker-образ): он выдаёт OIDC-токены, а страницу входа и проверку пароля оставляет нам. Пишем небольшое login-приложение **на Python** в фирменном стиле, которое вызывает ту же функцию проверки внешнего сервиса. Эту страницу смогут использовать и другие системы завода. Наша система становится обычным OIDC-клиентом. Запасной вариант без сторонних программ: сервис авторизации на Django + django-oauth-toolkit. Свой OIDC-протокол с нуля не пишем. Уже сейчас вход делается через интерфейс `AuthProvider`, чтобы переход на OIDC был заменой адаптера, а не переделкой.
- Интерфейс `AuthProvider` и варианты адаптеров (выбор в конфиге):
  1. **OIDC / OAuth2** (наш Ory Hydra + login-приложение или корпоративный провайдер): пользователь входит через провайдера, мы получаем токен и никогда не видим пароль. Самый безопасный вариант.
  2. **LDAP / Active Directory**: проверка пароля через bind по LDAPS.
  3. **Локальная проверка хэша**: внешний сервис отдаёт хэш пароля по табельному номеру, мы сравниваем локально. Пароль не покидает наш сервер. Нужен алгоритм хэширования (bcrypt, argon2, PBKDF2…).
  4. **Внешняя функция проверки**: передаём логин и пароль по защищённому каналу (TLS, по возможности mTLS) и получаем «да» или «нет». Пароль нигде не логируется и не хранится.
- После входа система выдаёт **свою сессию**: короткоживущий access-токен (JWT, ~15 мин) и refresh-токен в cookie `HttpOnly; Secure; SameSite=Strict`. Есть выход, отзыв сессий, блокировка после N неудачных попыток и журнал входов.
- **Первый администратор** создаётся командой при установке (по табельному номеру). Без этого в админку попасть нельзя.
- **Тестовые пользователи (обязательно, с первого этапа).** Вся система должна полностью работать и тестироваться без внешнего сервиса:
  - **локальные учётные записи** в нашей БД (пароль хранится как argon2-хэш), которые создаются командой или в админке и помечаются как локальные;
  - готовый набор тестовых пользователей с разными ролями и разными доступами к документам (например, «обычный», «аналитик», «админ», «без доступа к источнику X»);
  - **фейковый сервис-источник** (отдельный контейнер для разработки), который отвечает на проверку пароля, отдаёт тестовые документы и списки доступных id для тестовых пользователей;
  - в продакшене тестовые учётки и фейковый сервис выключаются настройкой. Остаётся одна **аварийная локальная учётка администратора** на случай, если внешний сервис недоступен (её вход пишется в аудит).

## 5. Ролевая система №1: доступ к функциям системы (RBAC)

- Права (permissions) — это атомарные действия, например: `search.common`, `documents.view`, `contradictions.view`, `contradictions.manage`, `documents.upload_manual`, `admin.users`, `admin.roles`, `admin.integrations`, `audit.view`, `skill.<имя>.use`.
- **Роли** собирает администратор в админке из галочек прав. Фиксированного набора ролей нет, есть только встроенные «Пользователь» и «Администратор», которые нельзя удалить.
- **Группы**: администратор создаёт группы (например, «Отдел ОТ и ПБ»), добавляет в них людей и назначает группам роли. Роли можно назначать и **конкретному человеку** напрямую. Итоговые права = объединение прав всех ролей человека и его групп.
- **Встроенная роль «Гость»** (неавторизованный пользователь): по умолчанию поиск, вопросы и просмотр общих документов. Её права администратор может сузить, но не может выдать гостю ничего сверх общих документов. **Любому вошедшему** по умолчанию доступно то же плюс документы, разрешённые ему источниками.
- **Навыки (агенты)** будут добавляться позже как плагины. У каждого навыка есть своё право `skill.<имя>.use`, и он появляется в интерфейсе только у тех, кому это право выдано. Пример будущего навыка: «проверить папку документов на соответствие ЕПОЗ». Сейчас нужен только каркас: реестр навыков, их права и пустое место в интерфейсе.
- Каждая проверка прав выполняется **на бэкенде**. Скрытая кнопка во фронтенде защитой не считается.

## 6. Ролевая система №2: доступ к документам

У каждой внешней системы своя ролевая модель, поэтому права на документы мы **не дублируем у себя**, а спрашиваем источник:

- У нас хранится реестр документов: наш id, id источника, id документа в источнике, номер, название, тема, дата и т. д. (так, чтобы документы можно было отличить друг от друга).
- При запросе пользователя система вызывает каждый подключённый источник с **табельным номером** пользователя. Источник возвращает список id документов, доступных этому пользователю (на одного человека могут прийти тысячи id).
- **Кэш прав:** ответ источника кэшируется на N минут (по умолчанию 5, настраивается). Кэш сбрасывается при входе пользователя и по кнопке в админке. Вызовы к разным источникам идут параллельно, с таймаутом.
- **Источник не ответил:** документы этого источника не показываются, пользователь видит предупреждение «Документы из системы X сейчас недоступны». Принцип fail-closed.
- **Фильтрация до поиска, а не после.** Векторный и полнотекстовый поиск, поиск по графу, противоречия, просмотр и скачивание документа фильтруются по списку разрешённых id на уровне SQL-запроса. LLM никогда не получает в контекст текст недоступного документа.
- **Противоречия** показываются только для пар, где пользователю доступны **оба** документа.
- Документы, загруженные вручную (см. п. 7), лежат в отдельной коллекции. Доступ к ним задаёт администратор (по группам или людям).
- **Общие документы (доступны всем, в том числе без входа).** Признак «общий» хранится у документа в нашем реестре. Он берётся из источника (источник отдаёт список общих id, например при запросе прав без табельного номера), а для ручных загрузок и коллекций его ставит администратор. Гостю в поиск, ответы, граф и просмотр попадают только общие документы.
- **Защита гостевого режима:** ограничение частоты запросов по IP, гостевые вопросы встают в очередь к LLM после вопросов вошедших пользователей, история гостевого чата живёт только в браузере, в аудит пишутся IP, время и вопрос. Гостевой режим целиком включается и выключается в настройках.
- Источников сейчас один, позже появится второй. Источник подключается адаптером (интерфейс `DocumentSource`) и настраивается в админке.

## 7. Загрузка документов из внешних сервисов

Сервис-источник отдаёт данные из своей БД через предоставленную функцию:
- **таблицу-шапку документов**: id (guid), тема, шапка, описание, дата изменения, дата удаления (мягкое удаление) и прочие поля;
- **одну или несколько табличных частей**, связанных со шапкой по guid документа;
- **бинарники файлов** документов: PDF и DOCX, внутри могут быть таблицы и сканы.

Что нужно сделать:
1. **Сборка документа из строк.** Шапка и табличные части превращаются в один структурированный текст (заголовок + поля + таблицы в Markdown). Он индексируется вместе с текстом прикреплённых файлов и ссылается на них.
2. **Парсинг файлов:** PDF (текстовый слой; для сканов OCR через Tesseract, rus+eng) и DOCX. **Таблицы сохраняются как таблицы** (Markdown) и не режутся посередине строки. Нарезка на чанки идёт с учётом структуры (заголовки, пункты, таблицы). У каждого чанка хранится документ, страница или раздел, номер чанка.
3. **Синхронизация:**
   - промежуточная (staging) таблица и проверки полноты: число строк табличных частей, размер файла, файл открывается и парсится;
   - инкрементальная загрузка по дате изменения с перекрытием окна;
   - идемпотентный upsert по id + версии (дата изменения);
   - мягкое удаление по дате удаления: документ пропадает из поиска;
   - **ночная сверка**: берём полный список id и дат изменения у источника, сравниваем с нашим реестром, догружаем недостающее, помечаем лишнее.
4. **Отчёт о полноте загрузки:** в админке и через API видно, сколько документов у источника, сколько загружено, сколько с ошибкой и почему, сколько в очереди. По каждому документу есть статус (в очереди / обрабатывается / готово / ошибка) и кнопка «повторить». API-эндпоинт, который может дёрнуть сам источник, отвечает, какие его документы загружены и с какой версией.
5. **Ручная загрузка** (для отладки) через UI доступна только по праву `documents.upload_manual`.
6. Объём: сейчас несколько тысяч документов, прирост около сотни в месяц. Первичная индексация может занять много часов, поэтому она возобновляется после перезапуска и показывает прогресс.

## 8. Поиск и ответы (RAG)

- Гибридный поиск: вектор (bge-m3) + полнотекстовый (PostgreSQL, русская морфология), объединение через RRF, затем **реранкер**, затем LLM.
- Ответ идёт **потоком** с heartbeat. В ответе **кликабельные ссылки на источники** (документ, страница или пункт), по клику открывается документ на нужном месте.
- **Многошаговый диалог** с историей чатов. История хранится 90 дней (настраивается).
- Если ответа в доступных документах нет, система прямо так и говорит и ничего не выдумывает. На общие вопросы, не связанные с документами («2+2»), отвечает отказом.
- Фильтры поиска: источник, коллекция, тип документа, дата, статус (действует / отменён).

## 9. Графовый RAG

Цель: отвечать на вопросы о связях. Например: «какие приказы сейчас действуют по теме X», «что отменило приказ 12», «кто ответственный за…», «какие документы касаются участка Y».

- Граф хранится **в PostgreSQL** в таблицах `entities`, `relations` и `entity_mentions`. Каждое упоминание сущности и каждая связь ссылаются на `chunk_id`, поэтому граф фильтруется по правам так же, как чанки. Сущность или связь видна пользователю, только если она подтверждена хотя бы одним доступным ему чанком.
- **Шаг 1 (правила, без LLM):** связи между документами «отменяет / изменяет / во исполнение / ссылается на» по реквизитам (номер, дата) регулярными выражениями. Это основа для поиска противоречий и статуса документа.
- **Шаг 2 (LLM):** извлечение сущностей (люди и должности, подразделения, оборудование, участки, сроки, нормативы) и связей той же единственной моделью в фоне, с JSON-схемой, с низким приоритетом. Перед полным запуском оцени время на нашем GPU на выборке и покажи прогноз: при ~10–30 секундах на чанк несколько тысяч документов могут обрабатываться днями. Предложи, как сократить время (фильтрация чанков, батчи, приоритет новых документов).
- Режимы поиска: обычный (чанки), графовый (сущности → связанные чанки) и смешанный. Сравни качество на тестовом наборе вопросов.
- Рассмотри готовые решения (LightRAG, Microsoft GraphRAG и т. п.) только как источник идей. Им нужна фильтрация по правам на уровне чанков, а она в них обычно не предусмотрена.

## 10. Противоречия

- Кандидаты: семантически близкие чанки из разных документов с нормативными формулировками, плюс пары, связанные графом. LLM оценивает пару по JSON-схеме. Проверенные пары кэшируются.
- Учитываются связи «отменяет / изменяет»: противоречие с отменённым документом не считается активным.
- Раздел виден только по праву `contradictions.view`. Пары показываются только если пользователю доступны оба документа.

## 11. Админка и «база знаний»

Идеи взяты из rag-web-ui, код не копируем.
- Коллекции документов (источник X, ручные загрузки, тематические).
- Карточка документа: метаданные (номер, дата, статус «действует / отменён», связи с другими документами), **просмотр чанков** и распознанного текста, кнопки «исключить из поиска», «переиндексировать».
- Источники: настройки подключения, расписание синхронизации, отчёт о полноте, ошибки, ручной запуск.
- Пользователи, группы, роли и права (п. 5).
- Журнал аудита: входы, вопросы (кто, когда, что спросил, какие документы попали в ответ), действия администраторов. Срок хранения настраивается.
- Состояние системы: загрузка GPU и VRAM, модели в Ollama, очередь задач.
- API с ключами доступа и документацией OpenAPI (для будущих интеграций).

## 12. Дизайн интерфейса: сделай его до вёрстки

**Сначала сгенерируй дизайн экранов**, покажи мне и только после согласования начинай вёрстку. Используй свои возможности генерации дизайна (Figma или интерактивные HTML-макеты).

- Фирменные цвета: **белый, серый, чёрный, оранжевый** (оранжевый — акцент для главных действий и важных статусов). Логотип приложен. Тёмная тема не нужна.
- Стиль: **современный, но под производственное предприятие**. Строгий, контрастный, с чёткой сеткой и крупными читаемыми элементами, без игривости. Должно читаться на обычном офисном мониторе и выглядеть как надёжный промышленный инструмент.
- Интерфейс полностью на русском.
- Экраны: вход; поиск и чат с источниками; просмотр документа с подсветкой найденного места; список документов с фильтрами; противоречия; админка (пользователи, группы, роли и права, источники и отчёт о синхронизации, карточка документа с чанками, аудит, состояние системы); состояния «загрузка», «ошибка», «источник недоступен», «нет доступа», «ничего не найдено».
- Сначала собери дизайн-систему (цвета, типографика, кнопки, поля, таблицы, бейджи статусов), потом экраны из неё. Во фронтенде используй те же токены.

## 13. Порядок работы (этапы)

Каждый этап заканчивается рабочим результатом, тестами и PR. Перед началом этапа коротко опиши план.

0. Каркас: репозиторий, docker-compose (proxy с TLS, app, worker, postgres, ollama), миграции, CI с тестами, офлайн-сборка. **Дизайн экранов на согласование.**
1. Вход (`AuthProvider` с фейковым адаптером для разработки), сессии, RBAC, админка пользователей, групп и ролей.
2. Источник документов: адаптер с фейковым сервисом, staging, сборка документа из строк, парсинг PDF/DOCX/таблиц/OCR, синхронизация, отчёт о полноте.
3. Доступ к документам через источник: кэш, fail-closed, фильтрация в SQL.
4. Поиск и чат: гибридный поиск, реранкер, стриминг, источники, история.
5. Граф: связи по правилам, затем извлечение LLM, графовый поиск.
6. Противоречия.
7. Аудит, состояние системы, API-ключи, каркас навыков.
7а. (Когда админы будут готовы) SSO: Ory Hydra + наше login-приложение на Python в фирменном стиле с проверкой через внешний сервис, переключение системы на OIDC.
8. Нагрузочный прогон на реальном GPU: сколько пользователей одновременно выдерживаем, задержка ответа, расход VRAM. Число одновременных пользователей пока неизвестно, поэтому заложи очередь к LLM и покажи пользователю его место в очереди.

## 14. Критерии качества

- Ни один тест не обходится без проверки прав: отдельные тесты на то, что пользователь **не** видит чужие документы ни в поиске, ни в ответе, ни в графе, ни в противоречиях, ни в просмотре файла.
- Секреты только в `.env`, в репозиторий не попадают. Пароли и токены не пишутся в логи.
- Тестовый набор из 30–50 вопросов с ожидаемыми документами для оценки качества поиска (recall@k) до и после изменений.
- README и инструкция установки на заводе офлайн, по шагам, для человека без опыта Docker.
- Открытые вопросы к заказчику веди отдельным списком в репозитории (`docs/open-questions.md`) и обновляй его.
